### 3. MetaParser facade + canonical types + SERP (commit `61a0ef8`)

New public API, all additive on 0.1.x:

| Module | What it gives you |
| --- | --- |
| `MetaParser` builder + `MetaGraph` | parse once, dispatch to every selected extractor via shared DOM |
| `FormatMask` | bitset for selective extraction (`FormatMask::JSON_LD \| FormatMask::MICRODATA`) |
| `FieldSource` / `FieldValue<T>` | per-field provenance tracking |
| `MetaGraph::get(field)` | cross-format query w/ priority: JSON-LD → microdata → RDFa → OG → Twitter → DC → meta → heuristic |
| `canonical::{Product, Article, Person, Organization, Event, Recipe, VideoObject, BreadcrumbList, Review, FAQPage, KnowledgeGraph, Money, Availability}` | cross-format merged entity types, each field wrapped in `FieldValue<T>` carrying source |
| `MetaGraph::canonical_*()` accessors | one-call merge for each canonical type |
| `serp::{parse_google, SerpGraph, FeaturedSnippet, PeopleAlsoAsk, OrganicResult, SiteLink, KnowledgeGraph}` | Google SERP parser lifted from `scraper_oxide` + stubs for Bing/DuckDuckGo/Yandex |
| `heuristics::apply` (+ per-rule submodules) | title/description/image/body/date/price fallback layer, enabled by default |
| `wikipedia::parse_infobox(html)` | Wikipedia infobox → `canonical::KnowledgeGraph` |
| `wikidata::parse_entity(json)` | Wikidata `Special:EntityData` JSON → `canonical::KnowledgeGraph` |
| `MetaParser::parse_reader<R: Read>` | streaming-friendly entry point (reads to String internally; real streaming is Phase 7 follow-up) |

**Internal refactor that made all of this possible:**
- `Extractor` trait in `extractors::common` now has `extract_from_dom(&Html, base_url)`. Every existing extractor got a sibling `extract_from_dom` function; the old `extract(html, base_url)` free functions became 2-line wrappers. The `microformat_extractor!` macro was updated to generate both variants automatically, covering all 9 h-* extractors in one edit.
- `include/meta_oxide.h` regenerated by cbindgen to expose the new public surface.
- `src/lib.rs` promoted three modules (`extractors`, `parser`, `types`) from `mod` → `pub mod` and added `pub mod canonical; pub mod heuristics; pub mod parser_facade; pub mod provenance; pub mod serp; pub mod wikidata; pub mod wikipedia;` with re-exports at the crate root.

**Additive-only constraint verified:** `reader_oxide` (which already
consumes `meta_oxide::extractors::*` directly) compiles unchanged
against this branch. `cargo check --features python --offline`,
`cd bindings/node && cargo check`, and the full workspace `cargo check`

### 4. Verification layers (commit `16565d4`)

Curated fixtures for Product (JSON-LD + microdata), Article, Recipe, Event, Breadcrumbs, FAQ, OG-only, heuristic-only, Wikipedia infobox, Wikidata entity, Google SERP. Each fixture locks the `canonical_*` output (or `MetaGraph::get` results) with `sort_maps => true` for determinism.
  - Review a legitimate behavior change: `cargo insta review`.

  - Scale up locally: `PROPTEST_CASES=10000 cargo test --test proptest_parser`.
- **cargo-semver-checks CI gate** (new `semver-checks` job in `.github/workflows/ci.yml`). Uses `obi1kenobi/cargo-semver-checks-action@v2`. Baseline is latest crates.io release. Enforces the additive-only contract with downstream consumers — any removed pub item or signature change now fails CI.

### Still-pending Tier 1 verification (from the audit)

4. **Coverage gate in CI.** llvm-cov already gives us 91.70% locally, but CI doesn't enforce a floor. Wire `cargo-llvm-cov` into `.github/workflows/ci.yml` with `--fail-under 90` on the `src/canonical/`, `src/parser_facade.rs`, `src/heuristics/`, `src/provenance.rs`, `src/serp/`, `src/wikipedia/`, `src/wikidata/` paths.    - `fuzz/fuzz_targets/wikidata.rs` → `wikidata::parse_entity` (likely finds `serde_json` panic paths first).
   - Optional: run on a nightly CI job with `cargo fuzz run <target> -- -max_total_time=300`.
   - **Estimated effort: 3-5 hours** (setup + corpus seeding + triaging the first round of findings).

### Known gaps flagged during the refactor (not in the Tier list, not blocking)

11. **JSON-LD top-level array support.** `extractors::jsonld::extract_from_dom` deserializes as single `JsonLdObject`; top-level arrays (`[{...}, {...}]`) are valid JSON-LD per spec but currently rejected. Discovered while writing integration fixtures; worked around by splitting into multiple `<script>` tags. **Fix is a breaking change to the extractor's return shape** (would need to return `Vec<JsonLdObject>` from each parse, flattening arrays) — not additive, not in scope for 0.1.x. Schedule for 0.2.0 if at all. Workaround meanwhile: consumers split their JSON-LD into separate script tags.

12. **RDFa in canonical entity merges.** `MetaGraph::get()` now consults RDFa (added during the audit), but `canonical::Product`, `canonical::Article`, etc. still don't read from `graph.rdfa`. Adding it is ~20 LOC per canonical type × 10 types = ~200 LOC + tests. **Priority:** low until a consumer actually needs it. Most schema.org data on the web is JSON-LD or microdata, not RDFa.

13. **Review promotion from embedded `Product.review`.** `canonical_reviews()` only surfaces top-level `@type: Review` objects. A `Product` with embedded reviews in its `review` field doesn't yield anything through `graph.canonical_reviews()`. The integration test `reviews_surfaced_from_embedded_product` locks in this behavior; flipping it would mean either (a) the JSON-LD extractor flattens `Product.review` into the top-level list, or (b) `Review::merge_all_from` walks the JSON-LD tree recursively looking for nested Review objects. Option (b) is cleaner. **Estimated effort: 1-2 hours.**

14. **Image ranking heuristic.** `heuristics::image` picks the first `<img>`. SOTA would pick the largest/most-prominent image using `width`/`height` attributes or CSS box heuristics. **Estimated effort: 2-3 hours** (+ fixture cases for edge cases like broken width attrs).

15. **Bing/DuckDuckGo/Yandex SERP parsers.** Currently stubs returning empty `SerpGraph`. `scraper_oxide` only needs Google today. Each engine is ~1 hour to lift the parser logic from `scraper_oxide::search::*`. Schedule on-demand.

16. **Python/Node/WASM binding coverage for the new facade.** Existing `extract_all` `#[pyfunction]` still works (builds a `PyDict`). New `MetaParser`, `MetaGraph`, `canonical::*`, `serp::*` are Rust-only. Exposing them to Python is a separate ~1-day task (new `#[pyclass]` wrappers + type stubs). Node/WASM bindings already compile against the new code via path dependency but don't expose the new API.

## Open architectural questions (parked)

- **Heuristic rule precedence vs. structured data.** Current rule: structured data always wins over heuristics. When a page has `og:description` AND a strong `<p>` heuristic match, we use OG. Double-check this against `reader_oxide`'s existing ordering before 0.2.0 — if reader_oxide has a different preference we should surface a flag.
- **`MetaGraph::get(field)` return type.** Currently owns the returned value (`Option<FieldValue<String>>`). An `Option<&FieldValue<String>>` variant would avoid small allocations but complicates the priority chain. Revisit if profiling shows it matters.
- **`FieldValue<T>` vs. parallel `*_source()` accessors on canonical types.** Current choice (wrap each field in `FieldValue<T>`) serializes cleanly to JSON but makes canonical types verbose in Rust usage (`product.name.as_ref().unwrap().value`). A parallel sidecar `sources: HashMap<String, FieldSource>` map would be ergonomically cleaner but breaks the "source travels with value" invariant. Decision locked for now; revisit if consumers push back.
- **Python facade for `MetaParser`/`MetaGraph`.** Currently Rust-only. Building the `#[pyclass]` wrappers is a day of work and pushes binding surface; defer until a Python consumer actually asks.
